# 在线 AI 聊天网站 — 需求分析

> 目标：实现一个类似 DeepSeek 聊天的在线 AI 网站，支持**文本 + 图片**多模态输入。
> 模型服务：硅基流动 (SiliconFlow) 上的 Qwen 多模态模型（OpenAI 兼容接口）。
> 第一版范围：**带用户体系**。

---

## 一、产品定位

- 形态：类似 DeepSeek / ChatGPT 的单页对话式 AI 助手。
- 关键差异：DeepSeek 本身不是多模态，本项目使用 Qwen 系列多模态模型，支持**上传图片 + 附带文字提问**。
- 用户体系：注册 / 登录，每个用户的会话历史独立保存、互不可见。

---

## 二、功能需求 (范围)

### MVP 核心（第一版必须）
| 功能 | 说明 |
|------|------|
| 注册/登录 | 邮箱+密码（或用户名+密码），密码哈希存储 |
| AI 对话 | 文本提问，AI 流式返回（打字机效果） |
| 多模态 | 上传图片（支持多张），随文字一起发给模型 |
| 会话管理 | 创建新会话、切换会话、删除会话 |
| 历史持久化 | 会话和消息存数据库，刷新/重登后可恢复 |
| 安全 | 会话归属校验（用户只能访问自己的会话） |

### 增强（第二版可选）
- Markdown 渲染 + 代码高亮（AI 常返回代码，强烈建议第一版就带上，体验差别很大）
- 消息复制、重新生成、停止生成
- 图片预览/缩略图、拖拽上传
- "正在输入"状态、错误重试
- 消息分页加载（历史较长时）

---

## 三、技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | 纯 HTML/CSS/JS | 用户指定；可先做单页，后续再演进到框架 |
| 后端 | Next.js | 用户指定；**注意**: Next.js 自带 React 前端，若前端要"纯 HTML/JS"，需要二选一（见下方冲突说明） |
| 数据库 | SQLite (better-sqlite3) / Prisma | 单机够用，无需单独部署 DB |
| 认证 | JWT + 密码哈希 (bcrypt/argon2) | 无状态会话，简单可扩展 |
| 模型 | 硅基流动 Qwen2.5-VL 系列 | OpenAI 兼容接口，流式（SSE），支持图片 |

### ⚠️ 选型冲突需要决策
你选了"纯 HTML/CSS/JS 前端" + "Next.js 后端"。Next.js 是一个**全栈 React 框架**，前端必须用 React 组件。两者直接冲突，有两个解：

1. **推荐：放弃 Next.js，改用轻量 Node 后端（Express 或 Fastify）+ 静态 HTML 前端**
   - 前端就是纯 HTML/CSS/JS 静态文件，后端只提供 API。完全符合你的前端选型。
   - 你仓库里有 [node/](d:/Code/AI-FullStack/node)，说明你熟悉 Node。

2. **保留 Next.js：前端就用 React**，放弃"纯 HTML/JS"
   - 这也是主流做法，Next.js 处理流式、SSR 都很方便。

> 这两个方案都需要你拍板，代码结构完全不同。见文末"待决策项"。

## 四、多模态 API 设计（硅基流动 / OpenAI 兼容）

请求结构（OpenAI `chat/completions`），文字和图片在同一消息中：

```json
{
  "model": "Qwen/Qwen2.5-VL-7B-Instruct",
  "stream": true,
  "messages": [
    { "role": "user", "content": [
      { "type": "text",   "text": "这张图里有几只猫？" },
      { "type": "image_url",
        "image_url": { "url": "data:image/jpeg;base64,....." } }
    ]}
  ]
}
```

要点：
- 图片以 **base64 data URL** 传给模型，**注意**单张图片大小和总配额上限（qwen-VL 对图片数量/分辨率有约束，多图会截断），前端可先做压缩。
- 接口地址：`https://api.siliconflow.cn/v1/chat/completions`（以官方文档为准）。
- **API Key 必须放在后端**，绝不能暴露在前端 JS 里（否则会被任意人窃取刷额度）。
- 流式返回用 SSE（`stream: true`），后端把模型 token 逐个转发给前端。

> ⚠️ 具体模型 ID、图片上限、图片格式支持请以硅基流动官方文档为准，这里给出的是通用接口形态。

## 五、系统架构

```
[浏览器] 纯HTML/CSS/JS
    │  (SSE 流式 / REST)
    ▼
[Next.js / Node 后端]
    ├── 代理层: 转发请求到硅基流动，含鉴权+key
    ├── 用户/认证: 注册、登录、JWT
    ├── 会话/消息: CRUD + 归属校验
    └── 流式管道: 前端<->模型 实时转发
    │
    ▼
[SQLite 数据库]         [硅基流动 API]
   users / sessions / messages
```

### 数据模型
```
users     (id, username, password_hash, created_at)
sessions  (id, user_id FK, title, created_at)
messages  (id, session_id FK, role[user|assistant], 
           content TEXT, images TEXT[存图片base64或引用], created_at)
```

---

## 六、核心流程

1. **登录**：发 JWT → 前端存 cookie/localStorage。
2. **新建会话** → 前端建立 SSE 连接，带 `Authorization`。
3. **发消息**：后端收到 → 组装 messages（注入该会话完整历史+图片）→ 调硅基流动 → 逐 token 转发回前端 → 前端流式渲染 → 完成后落库。
4. **切回历史会话**：前端按 session_id 拉取 messages 渲染。

---

## 七、非功能需求 / 风险

**安全**
- API Key 只存后端环境变量；前端永不含 key。
- 密码 bcrypt/argon2 哈希；JWT 签名密钥仅后端持有。
- **会话归属校验**：任何 session/message 查询都必须带 user 校验，防越权读取他人历史。

**性能**
- 流式输出必须分块返回，不能等服务端全部生成完。
- 图片上传前在前端压缩，减小体积与配额占用。

**兼容性**
- 模型 ID 与图片规则以硅基流动官方文档为准，需上线前核对。

## 八、待决策项

1. **前端/后端框架冲突**（必须定，见第三节）：
   - A) 放弃 Next.js → Express/Fastify + 静态 HTML（贴合你的纯 HTML 前端选型）
   - B) 保留 Next.js → 前端改 React
2. **具体模型 ID**：确认硅基流动账号里能用的多模态模型（如 Qwen2.5-VL-7B / Qwen2.5-VL-72B 等）。
3. 登录账号体系是否要**用户名+密码**即可，还是需要验证码/邮箱验证（第一版建议用户名+密码即可）。
4. AI 回答是否需要 Markdown 渲染（强烈建议第一版就包含，否则代码类回答不可读）。
